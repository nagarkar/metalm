# Auto-improve
Scope: the system that proposes, verifies, reviews and merges small improvements in every repo that imports metalm, and how a session checks its work. The system's code and schedule: `metalm-ops improve` (nagarkar/metalm#80; lenses and verifier: nagarkar/metalm#84; cadence and brake: nagarkar/metalm#88). It replaces codeteamlm.

## What the system does
(owner) Every rule in this section is the owner's. The owner, 2026-11-25: "every PR is like a small PR that just finds like one thing to fix and improves that"; "in cases where it's not a clear-cut improvement, I want that PR to be automatically canceled"; "if the changes are reasonable, commit them and merge them". 2026-11-26: "all of those things are, you know, open season for auto merging"; "Let the PRs get rejected"; "I don't want to wake up the Mac for this"; "have a minimum of all of the different lenses … to run on every repository at least every week", more often after "substantial activity"; "the break is a good safety net, but I don't want the break to happen and me to never find out that it happened".
- It runs at a few set times a day and never wakes the Mac; a time missed while asleep is skipped. Every applicable lens runs on every repo at least weekly; a repo also runs more often, up to every slot, in proportion to its recently changed lines, decaying over a week. Each run, a proposer agent works one lens (the one longest unrun) on one finding that deterministic measurements picked for it (nagarkar/metalm#97; the owner, 2026-11-26: "build deterministic tools … instead of relying on the agent to figure everything out every time"), and the finding must measurably improve. Lenses: readability, documentation, duplication, UI, tests, backend robustness (including security), frontend robustness, performance (with a before/after measurement), and design or requirements drift (code and its docstrings or `(owner)` rules disagreeing). One concern per PR, at most 5 files and 150 changed lines, tests included. Every lens may auto-merge.
- It never touches: rules marked `(owner)`, `guidelines/`, `CLAUDE.md`, `AGENTS.md`, skills' merge rules, `docs/generated/` (regenerated by the hook), migrations and schemas, `.env*`, secrets, launch agents and plists, metalm's `improve/braked.toml`, owner content (manuscripts, episodes, data folders), and any code that places orders, moves money or changes what a data pipeline writes (`scheduling.md`: same input, same output).
- Every PR carries two labels, `auto-improve` and `codex-automated`, a title starting `[auto-improve]`, and a body that opens with the block `Opened by the auto-improve system: Codex (codex exec), run by metalm-ops improve, run <id>, model <model>. Why: one small improvement per run under metalm guidelines/auto-improve.md.`, then: the lens, the claim and its evidence, the one thing it changes, why it is safe, the tests run, and the files touched. Every commit carries the trailers `Auto-improve-run: <id>` and `Co-Authored-By: Codex <noreply@openai.com>`.
- Three independent judges from a different provider than the writer (`coding.md`: cross-family judge), each posting a PR comment: a verifier that tries to disprove the claim with counter-evidence, a senior engineer, and a boundaries reviewer checking the list above. A refuted claim, any `reject`, a failing suite or a pre-commit failure closes the PR with label `auto-improve-rejected` and a comment naming the reason; the next run picks something else and never re-proposes a closed idea.
- Not refuted, two approvals and a green suite: the system merges it. This is the one exception to "Automation never merges, approves or closes" (`index.md#git-and-work-items`), and to the never-merges lines in `scheduling.md`'s checklists, for PRs labelled `auto-improve` only.
- Auto-closed PRs do not count toward pausing a routine (`scheduling.md`: "closed unreviewed twice running"). The brake: three PRs in a row rejected by the judges, or five runs in a row that failed without a PR (broken tests, a failed gate, an error; a run whose proposer found nothing is not a failure), stop that repo. The system adds it to `improve/braked.toml` in metalm through a PR labelled `auto-improve-brake`, merges that PR, and sends a SuperLM alert. Only the owner's word lifts a brake: a session removes the entry with `metalm-ops improve unbrake`.

## Session-start check
Every session in a repo, at start (`index.md#session`). Skip all of it in a repo that is not opted in. The owner, 2026-11-26: "review those in sub-agents in the background"; "go and check what was rejected and bring it to me for review".
0. Run `~/.claude/metalm/metalm-ops.sh improve status --repo <repo> --json` (`{"opted_in": false}`: stop here). If the repo is braked, lead with it: when, why, the brake PR's link, and each rejected PR or failed run with its link. Hand the diagnosis to a background subagent (the rejected diffs, the judges' comments, the run reasons), then bring the owner its account of what is going wrong and the concrete fixes it proposes. If not braked but no run has opened a PR in 7 days, say so with the last runs' reasons.
1. List system PRs no session has checked, merged and rejected: `gh pr list --state all --label auto-improve --search "-label:auto-improve-checked" --json number,title,state,mergedAt,closedAt,url --limit 50`, keeping `MERGED` and `CLOSED`. A missing label or an empty list: say nothing and go on.
2. Hand them to one background subagent and start the owner's task at once; never make the owner wait for it. The subagent reads each diff (`gh pr diff N`) and every review comment, against the boundaries above and the repo's `(owner)` rules, and returns one line per PR.
   - Merged: **fine** (no need to look), **worth knowing** (it changes something the owner sees or uses; say what), or **risky** (say why, and offer a revert PR; never revert unasked).
   - Rejected: **rightly rejected** (counted, not listed), or **worth reviving** (the judges were wrong or too cautious; say why in one line).
3. When the subagent returns, tell the owner the risky, worth-knowing and worth-reviving lines, each with its link, and the count of the rest. On the owner's word, revive one: apply its diff (`gh pr diff N | git apply`) on a new branch, open a PR that links the closed one, and merge it under the repo's `## Merging` rule.
4. Label each one checked: `gh pr edit N --add-label auto-improve-checked` (create the label with `gh label create auto-improve-checked --force` if missing). A risky one also gets `auto-improve-flagged`.
5. Also count open `auto-improve` PRs; name any open longer than a day (the system should have merged or closed it).
