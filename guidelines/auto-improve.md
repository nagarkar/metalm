# Auto-improve
Scope: the daily system that proposes, reviews and merges small improvements in every repo that imports metalm, and how a session checks its work. The system's code and schedule: nagarkar/metalm#80 (`metalm-ops improve`).

## What the system does
(owner) Every rule in this section is the owner's. The owner, 2026-11-25: "every PR is like a small PR that just finds like one thing to fix and improves that"; "in cases where it's not a clear-cut improvement, I want that PR to be automatically canceled"; "if the changes are reasonable, commit them and merge them".
- Once a day per repo, a proposer agent picks one improvement: a readability refactor, a wrong or stale docstring or comment, duplicated code merged into one function, a small UI fix. One concern per PR, at most 5 files and 150 changed lines, tests included.
- It never touches: rules marked `(owner)`, `guidelines/`, `CLAUDE.md`, `AGENTS.md`, skills' merge rules, `docs/generated/` (regenerated by the hook), migrations and schemas, `.env*`, secrets, launch agents and plists, owner content (manuscripts, episodes, data folders), and any code that places orders, moves money or changes what a data pipeline writes (`scheduling.md`: same input, same output).
- Every PR carries two labels, `auto-improve` and `codex-automated`, a title starting `[auto-improve]`, and a body that opens with the block `Opened by the auto-improve system: Codex (codex exec), run by metalm-ops improve, run <id>, model <model>. Why: one daily improvement per repo under metalm guidelines/auto-improve.md.`, then: the one thing it improves, why it is safe, the tests run, and the files touched. Every commit carries the trailers `Auto-improve-run: <id>` and `Co-Authored-By: Codex <noreply@openai.com>`.
- Two independent reviewer agents (one a senior engineer, one checking the boundaries above) each answer `approve` or `reject` with reasons, posted as PR comments. Any `reject`, a failing suite, or a pre-commit failure closes the PR with label `auto-improve-rejected` and a comment naming the reason; the next run picks something else and never re-proposes a closed idea.
- Two approvals and a green suite: the system merges it. This is the one exception to "Automation never merges, approves or closes" (`index.md#git-and-work-items`), and to the never-merges lines in `scheduling.md`'s checklists, for PRs labelled `auto-improve` only.
- Auto-closed PRs do not count toward pausing a routine (`scheduling.md`: "closed unreviewed twice running"); a repo where three PRs in a row are rejected is skipped until the owner rules.

## Session-start check
Every session in a repo, at start (`index.md#session`), before the owner's task:
1. List merged system PRs no session has checked: `gh pr list --state merged --label auto-improve --search "-label:auto-improve-checked" --json number,title,mergedAt,url --limit 50`. A missing label or an empty list: say nothing and go on.
2. For each, read the diff (`gh pr diff N`) and its review comments, and check it against the boundaries above and the repo's `(owner)` rules: does it change behaviour the owner relies on, a name the owner uses, a UI the owner reviews by eye, or anything outside its stated one concern?
3. Tell the owner in a short list, one line per PR with its link: **fine** (no need to look), **worth knowing** (it changes something the owner sees or uses; say what), or **risky** (say why, and offer a revert PR; never revert unasked).
4. Label each one checked: `gh pr edit N --add-label auto-improve-checked` (create the label with `gh label create auto-improve-checked --force` if missing). A risky one also gets `auto-improve-flagged`.
5. Also count open `auto-improve` PRs; name any open longer than a day (the system should have merged or closed it).
